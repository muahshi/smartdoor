# The Company Brain (SDOS Phase 1)

## Status

Phase 1 of SDOS, built on top of the Phase 0 foundation
(`ai/docs/SDOS_ARCHITECTURE.md`). This phase populates `ai/knowledge/`
with structured documentation of the SmartDoor business — the "Company
Brain." Nothing in this phase implements AI, dashboards, or workflows;
it is documentation only.

> Phase 2 (`ai/executives/cto/README.md`) builds directly on this Company
> Brain to fully define the AI CTO executive, in documentation only. See
> that folder for how an executive consumes the knowledge described here.
> Phase 5 (`ai/core/standards/README.md`) later standardized the shared
> *shape* every executive (CTO, COO, CFO, and future roles) is built
> from — this Company Brain remains the shared *content* layer; Phase 5
> did not change how executives read it.

## Purpose

Every future AI executive needs to understand the business before it
can reason about or act on it. Re-deriving that understanding from
scratch — by reading 86 SQL migrations, 67 service files, 40+ Edge
Functions, and a dozen partially-stale top-level docs — every single
time would be slow, inconsistent, and error-prone. The Company Brain is
a single, structured, pre-digested knowledge layer that captures that
understanding once, in one place, for reuse by every executive.

It is explicitly **not**:
- A chatbot or assistant interface
- A replacement for SmartDoor's actual database or code
- A place where business logic lives or executes

It **is**:
- A curated, navigable set of markdown documents describing the
  business, its data, its features, and its rules, derived from the
  real production repository

## Architecture

```
ai/knowledge/
  MASTER_INDEX.md      ← entry point; links to every domain below
  company/              company_profile.md
  products/              products.md
  features/               features.md
  database/                database.md
  services/                 services.md
  pages/                     pages.md
  documents/                  documents.md
  business/                     business_rules.md
  workflows/                     workflows.md
```

Each domain folder holds one primary markdown file (more may be added
later as the business grows) written in a consistent structured format
so an AI executive — or a human — can predictably find what it needs.

`MASTER_INDEX.md` is the single entry point. No executive should need
to know the folder structure by heart; it should start at the index and
follow links.

## How Future AI Executives Will Consume the Knowledge

1. An executive's prompt/context assembly step reads
   `ai/knowledge/MASTER_INDEX.md` first.
2. Based on the task, it selectively reads the one or two most relevant
   domain files (e.g. a CFO-flavored task reads `business_rules.md` +
   `products.md`; a CTO-flavored task reads `database.md` +
   `services.md`).
3. The executive treats everything here as **background context**, not
   as instructions or authority to act — any actual read/write against
   production data happens only through `ai/integrations/` (not yet
   built), under whatever approval gates that phase defines.
4. If the executive finds the knowledge base disagrees with what it
   observes directly in the database/code, it should treat the direct
   observation as correct and flag the discrepancy rather than silently
   trusting either source.

## How Knowledge Stays Synchronized With Production

This is the hardest and most important property of a Company Brain,
and it is **not automated as of this phase**. Until an automated sync
mechanism exists, the following applies:

- Every file in `ai/knowledge/` is a snapshot as of the date it was
  last written, generated by reading the actual repository at that
  time — not by inference or assumption.
- `documents/documents.md` explicitly flags known staleness in the
  *source* documents it indexes (e.g. `PROJECT_STATE.md` claiming
  "Phase 12" while the SQL history shows later work). The Company Brain
  itself should avoid inheriting that same staleness risk by being
  re-generated from the live repository periodically, not hand-edited
  to drift from it.
- **Recommended discipline for future contributors**: whenever a
  significant production change lands (new table, new service, new
  major feature, new business rule), the corresponding
  `ai/knowledge/` file should be re-read-and-regenerated from the
  updated repository in the same spirit as this phase — not patched
  from memory.
- A future phase may build an automated freshness-check (e.g. comparing
  `sql/` migration count or `services/` file list against what's
  documented) — this is a Phase 2+ candidate, not built here.

## Rules for Future Contributors (human or AI)

1. **Read the repository, don't assume.** Every fact in
   `ai/knowledge/` must trace back to something actually in the
   codebase or its documentation — not inferred from a product name or
   general SaaS conventions.
2. **Never let the Company Brain become the source of truth.** It
   describes production; it does not replace it. If a future executive
   is tempted to "just update the knowledge doc" instead of checking
   the live system before acting, that's a misuse of this layer.
3. **Additive, in-place updates only.** Regenerate a domain file in
   place when it goes stale; don't fork parallel copies or move content
   between folders without updating `MASTER_INDEX.md` accordingly.
4. **Flag, don't silently resolve, discrepancies.** When the knowledge
   base and the real repository disagree (as `PROJECT_STATE.md` and the
   real database currently do), write the discrepancy down rather than
   picking a side quietly.
5. **Stay inside `/ai`.** Nothing in the Company Brain build process
   modifies SmartDoor's production code, schema, UI, or business logic.
   Any exception (e.g. a documentation cross-link added to an existing
   file) must be explicit, minimal, and called out — none was needed or
   made in this phase.
