# Integration: Storage (Supabase Storage)

## Status

Documentation only, SDOS Phase 10. No client, connection, or credential
exists. Extends an existing production integration — see below.

## Purpose

SmartDoor already stores files in Supabase Storage buckets — QR code
images (`services/qr.js`, `QR_BUCKET`), visitor photos
(`services/activityCenter.js`, `VISITOR_PHOTO_BUCKET`), and voice
messages (`services/messaging.js`, `VOICE_BUCKET`, via signed URLs).
This integration would give a future SDOS capability read-only
visibility into bucket-level **metadata** (object counts, storage
usage, signed-URL issuance patterns) — never the file contents
themselves, and never upload/delete access.

## Supported Capabilities (Future, Documented Only)

- Read aggregate object counts and storage usage per bucket, as an
  operational/cost signal (relevant to a future CFO or CTO capability).
- Confirm existence/metadata (size, content-type, created-at) of a
  specific object path, without reading or exposing its content.

## Read-Only Access Policy

Governed by `ai/integrations/READONLY_POLICY.md`. This is the
integration where "read-only" most needs the distinction between
**metadata** and **content** to be explicit: even a "read-only" file
fetch is out of scope here. SDOS never calls
`.getPublicUrl()`/`.createSignedUrl()` to actually retrieve or expose
file bytes (QR images, visitor photos, voice recordings) — those are
sensitive/PII-adjacent by nature (a visitor's photo, an owner's voice
message) and stay entirely outside SDOS's documented scope, now and as
a future capability.

## Authentication Approach (Future)

If bucket-metadata access is ever needed beyond what
`services/monitoring.js`'s existing `supabase.storage.listBuckets()`
call already surfaces (readable via the `supabase/` integration), a
separately-scoped, metadata-only credential would be required — never
one with read access to object contents.

## Inputs

`capability`, `requested_by`, `scope` (bucket name; never an individual
object's content).

## Outputs

Bucket-level counts, sizes, and per-object metadata fields only
(`path`, `size`, `content_type`, `created_at`) — never signed URLs,
public URLs, or file bytes.

## Data Contracts

Follows `ai/integrations/DATA_CONTRACTS.md`, with `data` explicitly
excluding any URL or content field.

## Error Handling

`INTEGRATION_ERROR` on any failed/timed-out read, per
`ERROR_HANDLING.md`.

## Security Considerations

- **Content is categorically out of scope**, not just deprioritized —
  visitor photos and voice messages are PII/personal-data-adjacent by
  nature; this integration's future capability is capped at metadata
  permanently unless a separate, explicit, much more carefully-scoped
  future decision says otherwise.
- No signed URL is ever generated by this integration, since a signed
  URL is itself a capability to retrieve content, not just metadata.

## Rate Limits

None defined (no client exists).

## Future SDOS Capability

A future CTO capability could track storage growth trends
(`QR_BUCKET`, `VISITOR_PHOTO_BUCKET`, `VOICE_BUCKET` size over time) as
part of infrastructure cost monitoring. This remains metadata-only even
as a future capability — content access is not on this integration's
roadmap.
